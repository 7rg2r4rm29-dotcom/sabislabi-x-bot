# sabislabi-x-bot v2 — design technique

Assistant X pour **@sabislabi** (compte international en anglais). Ligne éditoriale depuis novembre 2026 : **« le futur arrive plus vite qu'on ne le croit »**, raconté avec des mots simples au grand public. Le compte donne la nouvelle lui-même, comme un compte d'alertes info (jamais « d'après tel site »), et chaque post part avec la photo officielle de l'actu quand elle existe — jamais une capture d'écran d'article (abandonnée le 14/11/2026).

## Ligne éditoriale et images (novembre 2026)

- **Public** : une infirmière, un chauffeur de taxi, un étudiant qui joue, un parent, un retraité. Ils ne suivent pas la tech ; ils s'arrêtent pour ce qui fait dire « attends, quoi ? » : de la science-fiction devenue réelle, un geste de tous les jours qui va changer, quelque chose d'un peu inquiétant. Consignes : `AUDIENCE`, `INTRIGUE`, `PLAYBOOK` (formes d'accroche), `TONE` (`bot/writer.py`).
- **Intriguer sans inventer** (`TRUTH`, `GROUNDING`) : le cadrage (« incroyable », « terrifiant ») est une opinion permise ; les faits viennent tous des articles cités. Une démo reste une démo, le futur se dit « bientôt / pourrait », pas de date, de prix ni de catastrophe absents de la source. La relecture (`FACTCHECK_PROMPT`) recale l'exagération et la certitude, pas l'émotion.
- **Zéro jargon, trois barrières** : les consignes (`PLAIN_WORDS`) ; un filtre côté code (`filters.find_tech_jargon` : LLM, API, benchmark, open-source… → motif « trop technique (mot) » et nouvel essai) ; la relecture par Claude, qui rend deux verdicts dans le même appel (`ok`/`issues` pour les faits, `plain`/`hard_words` pour la lisibilité). Au second essai, un texte dont les faits sont justes mais encore jugé « un peu technique » part quand même.
- **Rédaction en deux temps** :
  1. *La rédaction en chef* — `Writer._pick(brief, pool, n)` : Claude lit jusqu'à `MAX_ITEMS_PICK` (120) titres (`_headlines_block` : source · âge — titre — début du résumé), les consignes `EDITOR_PROMPT` + `PICKS` et le brief du post (`PICK_BRIEFS` : `news`, `tip`, `reactive`, `thread-timely|future|weekly`), et rend `picks` (numéros, le meilleur d'abord) ; liste vide = rien ne mérite un post, le créneau est sauté. Effort `low`.
  2. *La lecture* — `Writer._read_articles` : le texte des articles retenus (`sources.fetch_article_text`, ≤ 8 000 caractères, en parallèle, 45 s au plus en tout, jamais x.com) est rangé dans `NewsItem.body`. Un article illisible garde son résumé de flux. Le lecteur (`_ParagraphExtractor`, `article_text`) prend l'histoire qui suit le titre `<h1>` — jamais l'histoire suivante chargée plus bas, ni les cartes « à lire aussi » —, s'arrête à un intertitre « More on… / Related » une fois l'article commencé, écarte les encarts repérés à leur classe (bio, partage, promo ; un bloc WordPress « tag-… » n'en est pas un) et suit les redirections une à une, jamais vers x.com.
  3. *L'écriture* — `Writer._write_post` / `_thread_candidate` : Claude écrit d'abord cinq premières lignes possibles (`hook_options`), garde la meilleure, écrit à partir de ces seules histoires (article montré jusqu'à `ARTICLE_SHOWN`), cite ses sources (`source_ids`, obligatoires), désigne l'actu dont la photo accompagne le post (`visual_url` = `"[n]"`) et nomme sa forme d'accroche (`hook`, normalisée par `hook_shape` parmi `HOOK_SHAPES`, rangée dans `Draft.hook` puis dans les statistiques). Avec `POST_VERSIONS` > 1 (3 sur le serveur depuis le 19/11/2026 ; jamais pour un `gm` ni pour un thread, qui a déjà ses candidats), le premier essai d'un post écrit plusieurs versions séparées (`Writer._best_version`) : chaque appel `post-<kind>` voit les versions déjà écrites, et ce qui a fait refuser les fautives, avec la consigne d'en écrire une vraiment différente (`_other_versions`) ; les contrôles du code écartent les fautives ; un second avis classe les autres (`_rank_versions`, appel `choose-<kind>`, consigne `POST_JUDGE_PROMPT`, qui voit les histoires citées et les derniers posts du compte) ; la relecture (`_review_post`) suit ce classement et la première version sans reproche part, avec « meilleure de N versions » dans `Draft.reason`. Si aucune ne passe, le second essai est la réécriture guidée habituelle. `LLM_EFFORT_POST` (`high` sur le serveur ; vide = `LLM_EFFORT`) règle le temps de réflexion de l'écriture et du second avis (`_post_effort`) ; le choix de l'histoire reste en `low`, la relecture garde `LLM_EFFORT`.
  4. *Les garde-fous du code* — `filters.publish_problem` (liens, jargon, formules toutes faites `find_hype`, longueur, et `blocked_topic` : mort, guerre, armée, police, maladie, procès… refusés même quand seul le texte de l'article en parlait), `ungrounded_number` (un chiffre absent des histoires citées est refusé ; les VALEURS sont comparées : « 3 billion » = « 3bn » = « 3,000,000,000 » = « three billion », l'année en cours seulement si la source la donne), `_echoes_recent` (pas les mêmes trois premiers mots ni la même dernière ligne qu'un post récent), `is_too_similar`. Les posts récents montrés à Claude sont dans l'ordre de publication (`recent_all`). Un thread de plus de 7 tweets est réécrit, jamais coupé ; la numérotation « 2/ » est retirée, jamais un chiffre (« 2.5 million »).
  5. *La relecture* — `Writer._factcheck` : Claude liste chaque affirmation avec la phrase de l'article qui la soutient (`claims`) ; une seule non soutenue suffit à refuser. Un refus déclenche un second essai avec le motif (« reconstruire le texte, ne pas coller la correction en dernière ligne »), puis l'abandon.
- **Tri de l'actu avant le choix** : `sources.audience_factor` multiplie le score par 1,6 pour ce qui peut intriguer tout le monde (robots, jeux vidéo, premières mondiales, noms connus…), par 0,45 pour les sujets d'initiés (API, levées de fonds, puces…) et par 0,3 pour le commerce. Les flux généralistes sont filtrés (`"filter": "tech"` ou `"ai"`). Sujets militaires (`filters.MILITARY_RE`, qui comprend le contexte : « robot army », « combat spam » passent) et titres de bons plans clairs (codes promo, « 40% off », guides d'achat ; pas un « deal » entre entreprises ni un lancement « on sale ») ne sont jamais montrés. `top_for` plafonne chaque source, frais et reste compris.
- **On donne la nouvelle** (`NEWS_VOICE` dans `bot/writer.py`, doublé côté code par `filters.news_outlet_cited`) : le post dit le fait directement, sans jamais renvoyer au site, au journal ou au forum qui l'a racontée (« TechCrunch reports », « according to The Verge », « a report says », « points on Hacker News » → motif « cite un média » et nouvel essai). Qui a fait l'annonce, qui l'a dit ou mené l'étude reste nommé (« OpenAI says ») ; l'enquête ou le test d'un média s'écrit « an investigation found », « in a test ». Le nom d'un média n'est refusé que s'il est cité comme source : il reste permis quand il est le sujet. `NEWS_OUTLETS` couvre toutes les sources de `news_feeds` (un test le vérifie). La relecture (`FACTCHECK_PROMPT`) n'exige jamais le nom du site.
- **L'image, comme un compte d'alertes info** (`bot/visuals.py`, `prepare_media` → `(chemin, type, 2e image)`) : jamais une capture d'article, jamais de lien dans le post, jamais la marque d'un autre média sur l'image. Pages lues : d'abord les pages OFFICIELLES de l'histoire (`source_pages` : flux officiel, ou lien de l'article désigné par Claude, `Writer.pick_official_link`, filtré par `is_source_url`), puis — décision du propriétaire du 15/11/2026, `PRESS_MEDIA_ENABLED` — les articles cités eux-mêmes (`article_pages`, HTML relu depuis un cache). VIDÉO d'abord (`lead_video_url` : un FICHIER, jamais YouTube/Vimeo, flux m3u8/mpd, régie `AD_VIDEO_HOSTS` ni X ; `fetch_video_file` 200 Mo / 3 min ; `make_clip` : 30 premières secondes, H.264 High/AAC, 1280 px, 30 i/s, faststart, ffmpeg du paquet imageio-ffmpeg limité aux fichiers locaux ; trois images regardées par Claude, `Writer.video_is_usable`). Sinon PHOTO (`lead_image_url`, `photo_credit`, `normalize_photo`, `Writer.photo_is_usable` : ce dont parle le post, aucune marque de média ni filigrane d'agence). En mode prudent (`PRESS_MEDIA_ENABLED=false`), seules les pages officielles servent et `credit_problem` refuse d'office un crédit d'agence. 2e IMAGE (`SECOND_IMAGE_ENABLED`, jamais avec une vidéo) : Claude choisit logo de l'entreprise ou drapeau du pays en voyant la photo (`Writer.identity_plan`, `IDENTITY_PROMPT`) ; `identity_image_url` cherche l'entité sur Wikidata (`wbsearchentities`), prend P154 (logo) ou P41 (drapeau) — l'ACTUEL : rang « preferred » d'abord, jamais un ancien (qualificatif de fin P582) —, puis la vignette PNG sur Commons (licence libre, hôtes `WIKIMEDIA_FILE_HOSTS`) ; `compose_identity` la pose sur un carré de 1200 px (drapeau entier sur gris clair, logo centré sur blanc, ou sur noir s'il est clair) ; Claude vérifie (`Writer.identity_is_right`). Requêtes Wikimedia polies (`_wikimedia_json` : 1 s entre deux, un nouvel essai après HTTP 429, agent générique sans donnée personnelle). Sans photo, la 2e image seule ; sinon texte seul. Tous les téléchargements : redirections une à une, jamais X ni une adresse privée (`public_host`) ; `MEDIA_SEARCH_MAX_S` borne le tout. Item : `image_path` + `meta.second_image` ; Publisher : deux `upload_image` côte à côte ; carte Telegram : les deux images.
- **Rythme** : `POST_SLOTS=tip@14:30,news@19:00` (`tip` = « le futur arrive », `news` = « l'histoire du jour »), `THREAD_SLOTS=tue@14:30,sun@16:00` (genres `timely | future | weekly`), « ça vient de tomber » 1/jour au plus entre 12 h et 23 h 30. Sans histoire assez forte, un créneau est sauté ; si c'est Claude qui tombe pendant la rédaction (crédit, panne), le créneau est rédigé à son retour, tant que sa fenêtre est ouverte.
- **Ce qui marche** (consigne du propriétaire, 23/11/2026 : « insiste seulement sur les posts qui marchent, dans le même style, tant que ça marche ») — `bot/analytics.py`. Chaque post publié reçoit un sujet (`TOPICS` : jeux vidéo, voitures, robots, IA qui étonne, applis d'IA, gadgets, vie quotidienne, vie privée et arnaques, science, business, outils pour initiés), classé par Claude en un appel court (`Writer.label_topics`, appel `label-topics`, effort `low`), toutes les 6 h au plus (`Analytics.ensure_topics`, optionnel : cède au budget). `what_works()` calcule, sur 30 jours, la portée de chaque sujet, forme d'accroche, type et format comparée à un post habituel (1.0x) : `post_score` = vues + 30 par interaction ; poids divisé par deux tous les 7 jours (« tant que ça marche ») ; deux posts « habituels » imaginaires par groupe (un succès isolé ne fait pas une règle) ; un post viral compte 4 fois la normale au plus. `editor_notes()` (rédaction en chef) : sujets qui marchent (≥ 1.15x, 2 posts au moins), qui tombent à plat (≤ 0.85x, 3 posts au moins), nos meilleurs posts récents. `style_notes()` (rédacteur) : nos 3 meilleurs posts des 14 derniers jours, en entier, comme modèles de STYLE, et les formes d'accroche qui marchent. Jamais poussés, même quand ils marchent : les sujets pour initiés (`OFF_LINE_TOPICS`, 1,3x le 23/11/2026, sans doute l'ancien public tech) — la ligne reste le grand public. Trois posts prévus sur quatre suivent ce qui marche ; le quatrième essaie autre chose (`Bot._context`, `STYLE_TEST_SHARE` = 0,25, tirage à part : `Bot.style_rng`), sinon le compte ne découvrirait jamais ce qui pourrait marcher mieux ; noté dans `meta.style_test` puis `fmt.test`. Les posts « à chaud » et les 🔄 suivent toujours ce qui marche.
- **Tendances du jour** (même consigne : « analyse le marché et les tendances à chaque fois ») — `bot/trends.py`, `TrendWatch.block()`, avant chaque choix d'histoire (`Writer.set_editor_context` → bloc ajouté au message de `_pick`, jamais au rédacteur : ce n'est pas une source de faits). Sources gratuites, relevées une fois par heure au plus (`state.data["trends"]`) : recherches qui montent sur Google aux États-Unis et au Royaume-Uni (flux RSS `trending/rss`), pages Wikipédia en anglais les plus lues la veille (API Wikimedia, sinon l'avant-veille), première page de Hacker News (API Algolia), annonces officielles les plus aimées sur X depuis 48 h (prises dans `news_x_cache` : aucune lecture X de plus). Une source en panne garde son relevé 24 h. Filtre : ligne éditoriale (`off_limits_term`, `blocked_topic`), pages pour adultes, justice et violences. `TRENDS_ENABLED=false` les coupe. Le 22/11/2026, GTA VI et l'hypothèse de Riemann étaient parmi les dix pages Wikipédia les plus lues : nos deux meilleurs posts du mois.
- **Vidéos explicatives animées** (consigne du propriétaire, 23/11/2026 : « des vidéos éducatives, en mode docu, qui expliquent des choses intéressantes ») — `EXPLAINER_SLOTS` (vide par défaut ; `mon@14:30,wed@14:30,fri@14:30` sur le serveur) : la vidéo prend la place du post prévu à moins d'1 h d'elle (`EXPLAINER_CLEAR_MIN`) ; un jour de thread, le thread passe avant. Rédaction : `Writer.draft_explainer` = la rédaction en chef (`PICK_BRIEFS["explainer"]`, ce qu'une famille curieuse voudrait se faire expliquer), la lecture des articles, puis le script (`EXPLAINER_PROMPT`, sortie `EXPLAINER_SCHEMA` : `title`, 2 à 5 `scenes` de genre `fact` (texte + mot ou chiffre en grand), `steps` (2 à 4 étapes), `compare` (deux côtés), `quote` (les mots exacts d'une personne ou d'une entreprise nommée, jamais d'un média : `filters.names_news_outlet`), `ending`, et le post `text` de 200 caractères au plus). Tout ce qui s'écrit à l'écran passe par `publish_problem` (longueurs `EXPLAINER_LIMITS`), `ungrounded_number`, la mise en page réelle (`explainer.layout_problem`) et la relecture (`_factcheck` sur chaque écran + le post) ; un refus → une réécriture guidée, puis l'abandon (créneau sauté). Image : `bot/explainer.py` (Pillow + ffmpeg d'imageio-ffmpeg ; aucun code venu de Claude n'est exécuté) anime le script en 1080 × 1350, 24 i/s, 30 à 60 s, piste son muette AAC : étiquette « EXPLAINED », barre de progression, texte qui monte et apparaît, mot clé qui grossit, étapes une à une, deux cadres comparés, citation, fin avec « @sabislabi · Follow for the future, explained. ». Fond : la photo de l'actu (cherchée comme pour un post, sans extrait vidéo ni 2e image : `dataclasses.replace(settings, videos_enabled=False, second_image_enabled=False)`), nette sous le titre avec un dégradé sombre en bas, floue et sombre sous les explications ; sinon un fond bleu nuit animé. Fabrication mesurée sur le serveur (1 processeur) : 55 à 85 s. Vidéo impossible : la photo seule, sinon texte seul. Rédigée 1 h 30 avant en mode automatique (`AUTO_LEAD_MINUTES["explainer"]`). Publiée comme une vidéo d'actu (`upload_video`). `--preview explainer` la fabrique et l'envoie sur Telegram.

## Principes non négociables (sources officielles, oct. 2026)

1. **API officielle uniquement.** Aucun navigateur sur x.com (docs.x.com/developer-guidelines : « Non-API automation (scraping, browser automation) results in permanent suspension »). Le dossier `auth/` et `storage_state.json` disparaissent.
2. **Un humain valide chaque contenu écrit par Claude** avant publication (mode `APPROVAL_MODE=telegram`, par défaut). Raisons : les réponses générées par IA exigent l'accord préalable de X ; un compte entièrement automatique doit porter l'étiquette « Automated » ; Original Content Rewards exclut le contenu « created or posted using automated means » ; X a supprimé 42 000 comptes de réponses par chatbot en juillet 2026.
3. **Aucune réponse automatique sous les posts des autres, aucun like automatique.** L'API refuse d'ailleurs les réponses non « summoned » depuis le 23/02/2026 et a retiré likes/follows/citations du self-serve le 20/04/2026. Le **radar** propose une réponse rédigée, l'utilisateur la publie lui-même via un lien `x.com/intent/post?in_reply_to=…` qui ouvre l'app X.
4. **Pas de lien dans les posts publiés par l'API** (0,20 $ au lieu de 0,015 $ ; l'algorithme ne pénalise plus les liens, c'est une question de coût). Les noms de domaine (`claude.ai`) comptent comme des liens.
5. **Budget API X plafonné** (jour / mois), chaque appel est compté (`bot/costs.py`).

## Modèles partagés (`bot/models.py`)

```python
@dataclass
class NewsItem:
    id: str                 # hash stable (url ou id du post)
    title: str
    summary: str            # texte nettoyé, ≤ 600 caractères
    url: str
    source: str             # "OpenAI", "TechCrunch AI", "@claudeai"…
    published: datetime | None
    official: bool = False
    kind: str = "rss"       # rss | hn | x
    engagement: int = 0     # points HN ou likes X
    score: float = 0.0      # calculé par NewsHub (fraîcheur × poids × engagement × public)
    body: str = ""          # texte de l'article, lu seulement pour les histoires retenues

@dataclass
class Visual:
    kind: str               # "photo" (l'image de l'actu citée, prise à sa source) | "ai" ; « shot » : ancien nom
    target: str             # URL de la page (shot) ou description de photo (ai)

@dataclass
class Draft:
    kind: str               # gm | tip | news | thread | reactive
    texts: list[str]        # 1 texte, ou les tweets d'un thread
    visual: Visual | None = None
    poll: dict | None = None        # {"options": [...], "duration_minutes": 1440}
    sources: list[NewsItem] = field(default_factory=list)
    reason: str = ""        # pourquoi ce sujet (affiché sur Telegram)
    angle: str = ""         # genre de thread, angle de réponse…
    from_fallback: bool = False
    image_path: str | None = None   # renseignés par le planificateur (🔄 : l'image suit le texte)
    image_kind: str | None = None   # "shot" | "ai"
```

## Item (dans `state.data["items"]`)

Champs créés par `StateStore.new_item(kind, texts, **fields)` : `id, kind, status, texts, image_path, image_kind, poll, publish_at, expires_at, created_at, approved_at, published_ids, tg_message_id, regen_count, attempts, last_error, slot_key, slot_date, meta`.

- `kind` : `gm | tip | news | thread | reactive | explainer | comment_reply | radar` (`explainer` : vidéo explicative animée, depuis le 23/11/2026)
- `status` : `awaiting` (attend ta validation) → `approved` (programmé) → `publishing` → `published` ; ou `rejected | expired | failed` ; pour le radar : `suggested` → `dismissed | expired`.
- `meta` : `reason`, `angle`, `sources` (liste de {title,url,source}), `in_reply_to` (comment_reply), `comment_text`, `commenter`, `post_url`, `intent_url` (radar), `partial_ids` (thread interrompu), `retry_at`.
- `image_kind` : `video` (extrait MP4 de la vidéo officielle) | `photo` (photo officielle) | `ai` ; `shot` = capture d'écran, items d'avant le 14/11/2026.

## Cycle de vie d'un post planifié

1. `Bot.plan_slots()` : pour chaque occurrence de créneau (aujourd'hui et demain) dont l'heure de rédaction (`occurrence - lead`) est passée et qui n'a pas encore d'item (`state.slot_item_id(date, slot.key)`), récupère l'actu (`NewsHub.collect`), les notes perso, les notes de performance, appelle `Writer.draft_post(kind, …)` / `draft_thread(…)` (choix de l'histoire, lecture, 2 essais de rédaction ; sans histoire assez forte le créneau est sauté — seul l'ancien type `gm` a encore un texte de secours, en mode Telegram), prépare le visuel (`visuals.prepare`), crée l'item (`publish_at = occurrence + jitter aléatoire 0..PUBLISH_JITTER_MINUTES`, `expires_at = occurrence + APPROVAL_GRACE_MINUTES`), marque le créneau et appelle `Approvals.propose(item)`.
2. Telegram : carte avec boutons `✅ Valider` · `✏️ Modifier` · `🔄 Autre version` · `❌ Annuler` (+ `📲 Publier moi-même` = lien intent pour un post simple sans image).
3. `✅` : si `now < publish_at` → `approved` (« programmé à 13h32 ») ; sinon publication immédiate (`publish_at = now`).
4. `Publisher.publish_due()` : items `approved` avec `publish_at <= now` → upload image éventuel → `post` / `post_thread` → `published`, `state.add_published(...)`, carte mise à jour avec le lien.
5. Items `awaiting` dont `expires_at` est passé → `expired` (carte : « ⌛ expiré, rien publié »).
   Un item `approved` qui n'a pas pu partir à l'heure (bot arrêté) n'est plus publié au-delà de 3 h de retard (2 h pour un réactif, 12 h pour une réponse à un commentaire ; jamais pour un thread déjà en partie en ligne) : `expired` + message. `/reprendre` décale les posts validés en retard à `now + 3 min` (le temps d'annuler) et expire ceux qui ont trop attendu.
6. `APPROVAL_MODE=auto` (déconseillé, bloqué sans `AUTOMATED_LABEL_ACK=yes`) : l'item naît `approved`, la carte montre `❌ Annuler` / `✏️ Modifier` jusqu'à l'heure.

## Réponses à mes commentaires (`comments.py`)

Toutes les `COMMENTS_CHECK_EVERY_MINUTES` dans `COMMENTS_WINDOW` : `XClient.mentions(since_id)` (owned read). Garder les réponses à **mes** posts (`in_reply_to_user_id == mon id` ou conversation d'un de mes posts publiés), pas de moi-même, pas déjà traitées, pas blacklistées, pas hors ligne éditoriale. `Writer.draft_comment_reply(...)` → item `comment_reply` (`expires_at` +24 h) → carte `✅ Envoyer` · `✏️ Modifier` · `❌ Ignorer` · `🔗 Voir`. `✅` → `XClient.post(text, reply_to=comment_id)` immédiatement (réponse « summoned », 0,01 $). Si l'API refuse (`not_summoned`) → la carte propose `📲 Répondre moi-même` (lien intent). Plafond `COMMENTS_MAX_DRAFTS_PER_DAY`.

`COMMENTS_AUTO_REPLY=true` (choix du propriétaire, 18/11/2026 ; défaut `false`) : `Approvals.create_comment_item` crée l'item directement `approved` (`meta.auto`), `publish_at` = maintenant + `COMMENT_AUTO_DELAY_MINUTES` (3 min) ; la carte n'a que `❌ Annuler` · `🔗 Voir` ; le Publisher l'envoie à l'heure dite. Mêmes garde-fous que le mode manuel (`_rejection`, `Writer._vet`, une réponse par personne et par post et par jour).

## Radar (`radar.py`)

Toutes les `RADAR_CHECK_EVERY_MINUTES` dans `RADAR_WINDOW`, si le budget optionnel le permet : résout les ids des comptes (`user_ids`, mis en cache dans `state.radar.user_ids`), lit `RADAR_ACCOUNTS_PER_CHECK` comptes en rotation (`user_posts(since_id)`), garde les posts de moins de `RADAR_MAX_AGE_MINUTES` qui montent (`likes/min ≥ RADAR_MIN_LIKES_PER_MIN`), hors bruit / sujets bloqués, un seul par compte et par jour ; `Writer.draft_radar_reply(...)` → item `radar` (`status="suggested"`, `expires_at` +90 min) → carte `📲 Répondre dans X` (lien intent) · `🔄 Autre réponse` · `❌ Passer` · `🔗 Voir le post`. **Jamais de publication par l'API.** Plafond `RADAR_MAX_PER_DAY`.

## Posts réactifs

Toutes les `REACTIVE_CHECK_EVERY_MINUTES` dans `REACTIVE_WINDOW`, hors ±`REACTIVE_SLOT_GAP_MINUTES` autour d'un créneau (`Bot._slot_gap` ; sans ce réglage : `REACTIVE_MIN_GAP_MINUTES`, 60 min, qui reste l'écart entre deux posts à chaud ; 10 min sur le serveur depuis le 19/11/2026, car avec 60 l'actu chaude n'était pas regardée de 18 h à 20 h), sous `REACTIVE_MAX_PER_DAY` (1 par défaut), et seulement s'il y a une actu fraîche (< 12 h) que la rédaction n'a pas encore examinée et qui peut valoir un post immédiat — officielle, qui décolle, ou de nature à intriguer tout le monde (`Scheduler._appeal`), jamais réservée aux initiés (`REACTIVE_MAX_CHECKS_PER_DAY` appels par jour au plus : 6 par défaut, 30 sur le serveur depuis le 19/11/2026, avec `REACTIVE_CHECK_EVERY_MINUTES=15` ; à 6, le plafond était atteint vers 20 h 30 et le bot ne voyait plus les annonces du soir. La mémoire des flux et du résultat, 20 min, tombe juste sous l'intervalle quand il est plus court — `NewsHub._cache_ttl`, 13 min pour 15 — sinon une vérification sur deux relirait la mémoire ; les comptes X gardent leur propre rythme, `X_REFRESH_MINUTES`, car chaque lecture y est payée) : `Writer.draft_reactive(news)` = la rédaction en chef (`_pick("reactive", …, 1)`, « la plupart du temps, la bonne réponse est une liste vide »), puis le même chemin d'écriture qu'un post. Si oui : item `reactive`, `publish_at = now`, `expires_at = now + 180 min`.

## Analytique (`analytics.py`)

- `refresh_metrics()` toutes les 3 h : `my_recent_posts()` → `public_metrics` (impressions, likes, réponses, reposts, signets) rangées dans `state.published[*].metrics` ; agrégats par type et par créneau dans `state.data["performance"]`.
- `performance_notes()` → 3-6 lignes pour Claude (meilleurs types et créneaux, posts avec ou sans image…), suivies de `style_notes()` (nos meilleurs posts comme modèles de style) ; `editor_notes()` va à la rédaction en chef (voir « Ce qui marche » plus haut).
- `ensure_topics(labeler)` : le sujet de chaque post (`published[*].topic`), classé par Claude, toutes les 6 h au plus.
- `daily_report()` (à `HEALTH_REPORT_AT`) et `weekly_report()` (à `WEEKLY_REPORT_AT`) → texte Telegram en français.

## Coûts estimés

API X (payée par la carte du propriétaire chez X ; mi-novembre 2026 ≈ 0,80 $/jour, surtout des lectures) : 3 posts/jour + 3 threads/semaine (rythme du serveur depuis le 18/11/2026) ≈ 3 $/mois ; réponses aux commentaires 0,01 $ pièce ; radar coupé sur le serveur depuis le 18/11/2026 (`RADAR_ENABLED=false`) pour compenser ; lectures radar/actu (optionnelles) plafonnées à 75 % de `X_BUDGET_MONTHLY_USD`, étalées jour par jour (au plus `min(80 % du plafond du jour, 75 % du mois / nb de jours)`) : le dernier quart du mois reste toujours disponible pour publier. Claude : ~15-40 appels/jour (chaque post = un choix d'histoire, une rédaction, une relecture, un regard sur la photo ; les vérifications « à chaud » ne coûtent que le choix), soit de l'ordre de 30 à 35 $/mois avec `claude-opus-5-5` (4 $ / 20 $ par million de tokens ; mesuré en novembre 2026 : environ 1,10 $ par jour, dont 0,30 $ d'optionnel — radar et vérifications « à chaud »), environ moitié moins avec `claude-sonnet-5-5`. Plafond : voir « Budget Claude du mois ».

### Budget Claude du mois (18/11/2026)

Le compte API du bot (console Claude, organisation individuelle du propriétaire) reçoit chaque mois les 200 $ de crédits compris dans son forfait Claude Ultra (crédits « promotionnels », réclamés le 18/11/2026 ; ils expirent à la fin de chaque cycle, sans report). Le propriétaire veut que le bot n'en consomme pas plus de **195 $ par mois** (35 $ jusqu'au 18/11/2026 au soir) : `CLAUDE_BUDGET_MONTHLY_USD` (défaut du code 35, 195 dans le `.env` du serveur, 0 = pas de plafond). Consigne : Claude n'est payé que par ces crédits gratuits, jamais par sa carte ; la recharge automatique de la console reste coupée, et à crédit épuisé l'API refuse simplement (`account_problem`).

- Le coût de chaque appel est estimé à partir des jetons (`MODEL_PRICES`, à 1 % près de la console) et rangé par jour dans `state.llm_usage.days`. Les essais faits à la main pendant que le service tourne (`--preview`, `--check`, scripts) utilisent `LLM(…, manual=True)` : leur coût va dans `state/llm_manual_usage.json` (le service lit ce fichier et ne l'écrit jamais, car il réécrirait son état par-dessus). `LLM.spent_month()` additionne les deux.
- Plafond atteint (`over_budget`) : plus aucun appel (`_call` rend None, `paused()` vrai, donc ni créneau ni post à chaud), un seul message Telegram dans le mois (`Bot.maybe_alert_claude`, marque `state.claude_budget.reached`), rappel dans le récap du matin ; reprise automatique le 1er.
- Avant le plafond, l'optionnel cède le premier (`LLM.optional_ok`, `Bot._claude_optional_ok` dans `tick`) : radar, posts à chaud et réponses aux commentaires ne tournent que si `dépensé + ESSENTIAL_SHARE (75 %) × plafond × jours restants / jours du mois ≤ plafond` ; les posts planifiés continuent jusqu'au plafond.
- À 80 % (`BUDGET_WARN_SHARE`) : un message Telegram, une fois par mois (`Bot.maybe_warn_claude_budget`).
- Panne du 17/11/2026 : crédit prépayé épuisé (« Your credit balance is too low »), deux créneaux perdus ; le bot avait prévenu sur Telegram (`account_problem`).
- Deuxième barrière, hors du code (18/11/2026) : sur la console, la clé du bot est dans un espace de travail réservé, « Bot X », limité à 195 $ par mois (35 $ jusqu'au 18/11/2026 au soir). La limite de l'organisation (500 $) et l'espace « Default » ne sont pas touchés, pour les autres projets du propriétaire. Le compteur du bot étant un peu pessimiste, c'est lui qui s'arrête le premier en temps normal.

## Installation (`deploy/`)

- `push_from_mac.sh` (sur le Mac, bash 3.2) : assistant guidé. Envoie le code (tar via ssh, jamais `config/.env`) dans un dossier unique `~/xbv2_stage_<date>` ; lance `precheck.sh` et ne demande que les clés qui ne marchent pas (ouvre la bonne page, `set_secrets.sh CLE…` via `ssh -t`, `telegram_setup.sh` pour le jeton et le chat privé) ; propose la rotation des clés ; lance `deploy.sh` détaché (`nohup setsid`, journal `~/xbv2_deploy_<date>.log`) et le suit avec `follow.sh` : une coupure ssh n'interrompt pas l'installation.
- `precheck.sh` (serveur) : instantané `pip freeze`, mise à jour des bibliothèques, puis `bot.main --check` de la NOUVELLE version avec le `.env` installé (`XBOT_ENV_FILE`) ; dernière ligne `PARTS telegram=… x=… claude=… images=…` (ok | missing | bad | group | auth | credits | forbidden | wrong_account | error ; `images=bad` n'est qu'un avertissement : le bot publierait en texte seul).
- `deploy.sh` (serveur) : verrou ; refus si publication en cours (`--busy-check`, ou horaires fixes de la v1) ; bibliothèques + `pytest` sur la nouvelle version ; arrêt du service ; sauvegarde datée (`backup_deploy/<date>/` + manifeste `.xbot_backup`, 5 gardées) ; installation de `bot/ deploy/ tests/` ; `settings.json`/`content.json` remplacés seulement s'ils n'ont pas été modifiés (copie livrée dans `config/.shipped/`, sinon `….nouveau`) ; `migrate_env_v2.sh` ; `--check` réel ; redémarrage. Tout échec ou interruption (trap INT/TERM/HUP) après l'arrêt → `restore_backup.sh`, bibliothèques remises (`pip freeze`), relance, message Telegram ; une restauration incomplète arrête le bot et le dit. Dernière ligne `FIN_DEPLOIEMENT <code>`.
- `restore_backup.sh` : remet une sauvegarde (code + JSON ; l'état seulement s'il change de format ; `.env` seulement pour annuler un déploiement raté) ; continue malgré une erreur et la signale ; remettre la v1 (navigateur) à la main exige de taper `OUI`.
- `cleanup_v1.sh` : une fois la v2 en service, supprime `auth/` (session X du navigateur), les copies de l'ancien `.env`, les restes v1 et les clés SSH privées égarées dans le dossier.
- Points d'entrée de test : `XBOT_APP_DIR`, `XBOT_SERVICE=""`, `XBOT_SUDO`, `XBOT_SKIP_PIP|TESTS|CHECK`, `XBOT_CLOCK`, `XBOT_SSH`, `XBOT_HOST`, `XBOT_OPEN`, `XBOT_NO_TTY`, `XBOT_NO_TELEGRAM`, `XBOT_TELEGRAM_API`.
